# DailyDiet 调研报告

> 目标：做一个安卓端饮食热量记录 App，覆盖「饮食摄入 / 运动消耗 / 每日热量预算 / 减脂热量缺口目标」，定位参考薄荷健康。
> 调研日期：2026-10-05
> 说明：标注「已核验」的数据来自本次实际抓取的公开页面；未标注的为行业通行做法或个人经验判断，落地前需再确认。

---

## 一、一句话结论

这个方向**可行，但不要和薄荷健康正面拼食物库规模**。
薄荷用 15 年积累了 100 万+ 条食物数据（应用宝官方介绍），这是它的护城河，也是新项目最难复制的部分。

真正可行的切入点是：

1. **记录足够快**（搜索联想、常吃、拍照/语音、条码）；
2. **本地优先、无广告、隐私干净**；
3. **把「热量缺口」做成一件事**：摄入、运动、体重趋势三者联动，而不是各记各的。

食物库数据处理和合规备案，是这个小项目最容易翻车的两个地方，要提前定方案。

### 2.3 差异化机会

薄荷的问题正好是新项目的机会：

- **广告和电商导流重**，界面越来越重；
- **强制账号/云同步**，隐私敏感用户不放心；
- **记录流程仍有摩擦**，一顿饭要点很多次。

可打的牌：

- 纯本地运行也能完整使用，账号同步可选；
- 无广告 / 一次性买断；
- 「今天还能吃多少」一屏看清，不做二级页面；
- 运动与缺口联动，直接告诉用户「今天要走多少步/跑多久才能补上」。

### 2.4 政策风向（利好）

**已核验**：国务院《国民健康"十五五"规划》（国发〔2026〕23 号，2026-07-07）明确提出：

- 实施**合理膳食行动和健康体重管理行动**，推动减盐、减油、减糖；
- 实施国民营养计划，完善营养健康标准体系；
- 鼓励医疗机构设立**体重管理门诊**；
- 推进全民健康数智化，有序推动数智技术在**健康管理**场景的应用；
- 加快健康消费提质扩容。

结论：体重管理和饮食记录属于政策鼓励方向，但**不能碰医疗宣称**（见第六节）。

## 三、核心功能拆解

### 3.1 必须有的（MVP）

1. **新手引导 / 目标设定**
   性别、年龄、身高、当前体重、目标体重、目标周期、活动水平。
2. **每日热量预算**
   由 BMR / TDEE 自动算出「每日可摄入热量」和「热量缺口」。
3. **饮食记录**
   搜索食物、选份量/单位、按早/午/晚/加餐归类、常吃/最近快捷添加、自定义食物。
4. **运动记录**
   运动类型 + 时长（或距离）+ 强度 → 自动估算消耗；支持手动覆盖。
5. **今日面板**
   `已摄入 − 运动消耗 = 净摄入`；剩余可摄入；蛋白质/脂肪/碳水三项。
6. **体重与趋势**
   体重曲线 + 7 日均线 + 周报。

### 3.2 提体验的（第二阶段）

- 条码扫描（包装食品）；
- 拍照识别（AI 估计食物和份量）；
- 自然语言记录（"一碗米饭 + 两个鸡蛋"）；
- 喝水记录、断食计时；
- 数据导出（CSV）；
- Health Connect 步数/运动同步；
- 桌面小组件、通知提醒。

### 3.3 可以砍掉的

- 社区、好友动态、排行榜（内容审核 + 运营成本高）；
- 电商、代餐带货（重供应链）；
- 复杂社交分享。

## 四、算法设计

### 4.1 基础代谢 BMR（推荐 Mifflin-St Jeor，1990）

```
男：BMR = 10 × 体重(kg) + 6.25 × 身高(cm) − 5 × 年龄 + 5
女：BMR = 10 × 体重(kg) + 6.25 × 身高(cm) − 5 × 年龄 − 161
```

比 Harris-Benedict 旧公式更贴近现代人群，是目前主流 App 的选择。

### 4.2 每日总消耗 TDEE

```
TDEE = BMR × 活动系数
```

| 活动水平 | 系数 |
|---|---|
| 久坐（几乎不运动） | 1.2 |
| 轻度（每周 1–3 次） | 1.375 |
| 中度（每周 3–5 次） | 1.55 |
| 高度（每周 6–7 次） | 1.725 |
| 极高（体力工作/一天两练） | 1.9 |

### 4.3 热量缺口与每日目标

```
1 kg 脂肪 ≈ 7700 kcal
每日目标缺口 = (当前体重 − 目标体重) × 7700 ÷ 目标天数
每日可摄入 = TDEE − 每日目标缺口
```

**必须加安全边界**（否则应用会被判定为不健康引导）：

- 建议每日缺口控制在 **300–500 kcal**；
- 一般不超过 **750–1000 kcal**；
- 每日摄入不低于女性 **1200 kcal** / 男性 **1500 kcal**；
- 目标周期过短时提示用户放宽。

### 4.4 运动消耗

```
kcal = MET × 体重(kg) × 小时数
```

等价写法：`kcal = MET × 3.5 × 体重(kg) ÷ 200 × 分钟数`。

MET 值建议参考 **Compendium of Physical Activities**（2011 版，另有 2024 Adult Compendium 更新），自建一份「运动类型 → MET」表即可，不必全量导入。

### 4.5 宏量营养素分配（减脂期参考）

- 蛋白质：1.2–2.0 g/kg 体重（减脂期可偏高，保留肌肉）；
- 脂肪：占总热量 20–30%；
- 碳水：剩余热量。

### 4.6 重要提醒

BMR / TDEE / 运动消耗都是**估算**，个体误差通常 ±10–20%。
产品里要明确写「估算值，仅供参考」，并在用户体重变化后自动重算，否则用户会认为"算不准"。

## 五、食物数据库选型（最关键决策）

### 5.1 候选方案对比

| 方案 | 规模 | 授权 | 中文支持 | 成本 | 风险 |
|---|---|---|---|---|---|
| **USDA FoodData Central** | 数十万条（Foundation / SR Legacy / FNDDS / Branded） | **公有领域 CC0，可商用**（已核验） | 英文 | 免费 | 中式菜品、中餐主食覆盖差 |
| **Open Food Facts** | 全球 4,793,579 条（已核验，2026-10-05） | 数据库 ODbL（**传染性**），图片 CC-BY-SA | 部分 | 免费 | 中国大陆标签仅 1,722 条（已核验），条码覆盖率极低；ODbL 要求衍生库同样开放 |
| **中国食物成分表标准版第 6 版（开源转录）** | 1,677 条，63 个 JSON，约 1.25 MB（`Sanotsu/china-food-composition-data`） | **仓库无 License**，原书受版权保护 | 中文，权威 | 免费 | **商用有侵权风险**，只适合原型验证 |
| **foodwake 数据集** | 1,643 条（`LuckyHookin/foodwake`） | 仓库 Apache-2.0，但数据爬自 foodwake.com，源头授权存疑 | 中文 | 免费 | 数据准确性、来源合规需评估 |
| **自建 / 众包 UGC** | 自行积累 | 自有 | 中文 | 人力成本高 | 需要用户协议授权用户贡献数据 |
| **商业 API** | 菜品识别、条码查询 | 商业授权 | 中文 | 按量付费 | 依赖第三方，成本随用户量增长 |

### 5.2 建议路线

1. **MVP 阶段**：用开源中式数据集清洗后打底 + USDA 做生鲜食材补充 + 用户自定义食物兜底。
   这一步只用于验证产品，不对外宣称数据权威性。
2. **正式商用前必须解决授权**，三选一：
   - 自己录入核心食物（几百条常用食物先跑起来）；
   - 众包 UGC，并在用户协议中明确「用户贡献数据可用于产品」；
   - 购买商业食物库授权。
3. **不要直接搬运薄荷的食物数据**，这是明确的法律风险。

> 这是整个项目最大的不确定性。建议第一周就把食物库来源定下来，否则后面返工成本很高。

## 六、技术选型建议

### 6.1 推荐栈（原生 Android）

| 层 | 选择 |
|---|---|
| 语言 / UI | Kotlin + Jetpack Compose + Material 3 |
| 架构 | MVVM + Clean Architecture，单 Activity |
| 本地存储 | Room（食物库预置为 asset SQLite，首次启动导入） |
| 配置 | DataStore（Proto 或 Preferences） |
| 依赖注入 | Hilt |
| 后台任务 | WorkManager |
| 图表 | Vico 或 Compose Charts |
| 网络（可选） | Retrofit + OkHttp 或 Ktor |
| 最低版本 | minSdk 26（Android 8.0），targetSdk 跟随最新 |
| 运动数据 | **Health Connect**（Google Fit API 已弃用，新项目不要再接） |
| 推送（国内） | 华为/小米/OPPO/vivo 厂商通道，或极光/个推 |

### 6.2 备选：Flutter

- 优点：跨平台，OpenNutriTracker / FitBook 已验证可行；
- 缺点：Health Connect、后台任务、国内推送的体验不如原生；
- 如果明确只做安卓，**建议直接 Kotlin 原生**。

### 6.3 后端策略

- **MVP 不做后端**：纯本地，零服务器成本，隐私好，合规面小；
- 需要账号云同步时再补：Ktor 或 Spring Boot + PostgreSQL；
- 注意：一旦有服务端，服务器和域名也需要 ICP 备案。

## 十、风险清单

1. **食物库授权与准确性**：最大风险，决定能不能商用。
2. **记录成本高导致流失**：用户记录 3 天就放弃是这类 App 的头号死因，快捷记录体验必须优先做。
3. **估算误差引发不信任**：需要透明展示计算逻辑，并提供手动调整。
4. **合规**：备案、软著、隐私、商店审核，周期可能比开发还长，要并行推进。
5. **正面竞争**：不要在食物库规模上硬碰薄荷。

## 十二、工程验证与打包决策（2026-10-05 更新）

用户决定**以 GitHub Actions 作为唯一验收入口**，本地不承担构建与测试职责：

- 开源仓库使用 GitHub Actions 的免费额度；
- 每次 push / pull request 自动跑单元测试、构建 debug APK；
- 打 `v*` tag 时使用仓库 Secrets 中的签名信息构建 release APK；
- 构建产物通过 Actions Artifact 下载，不依赖本地 Gradle、SDK 或 Android Studio。

产物清单（debug 与 release 一致）：

- `DailyDiet-<version>[-debug].apk`
- `checksums-md5.txt`（`<md5>  <filename>`）
- `checksums-sha1.txt`（`<sha1>  <filename>`）

工作流在生成校验文件后会执行 `md5sum -c` 和 `sha1sum -c` 自检；tag 发布时
还会把 APK 与两个校验文件附加到对应的 GitHub Release。

版本号格式统一为 `MAJOR.MINOR.yyyyMMdd`，例如 `1.0.20261005`：

- 唯一来源是 `gradle.properties` 中的 `dailyDiet.versionName`；
- `versionCode` 默认由日期加 1 位同日修订号推导，`1.0.20261005` 对应 `202610050`；
- release tag 必须写成 `v1.0.20261005`，tag 值会在构建时覆盖 `versionName`，保证 APK 与 tag 一致。

对应工作流：`.github/workflows/android.yml`。

这意味着本地只需要保持代码可读、依赖版本锁定即可。Gradle Wrapper、JDK 版本、
Android SDK 全部在 CI runner 上重建，避免“我电脑能跑”的问题。

签名 Secrets 清单：

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`
